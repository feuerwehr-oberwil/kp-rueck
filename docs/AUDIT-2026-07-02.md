## ASAP — silent data loss in the core flow

These are the ones that can actually jeopardize a live operation. Fix first,
ideally as one batch, and add a regression test so they can't recur.

> each with regression tests. C1: per-incident `UpdateBatcher`
> (`frontend/lib/update-batcher.ts`) + unit suite. C2: `NetworkError` thrown for
> mutations, GETs still soft-degrade + unit suite. C3: migration `b3d7f2a9c1e8`
> + enum/constraint + parity test over all `NotificationType` values. C4: sync
> endpoints admin-only (`/status` and `/logs` stay authenticated-user for the

### C1 — Rapid consecutive edits silently drop the first one
- **What:** `updateOperation` uses a single shared debounce timer for *all*
  incidents; the non-critical path re-arms it with only the newest call's payload.
  Two edits within 500 ms (drag A, then drag B / set priority / J-K move) → A's
  PATCH is never sent. Card looks committed, snaps back on next poll, no error.
- **Where:** `frontend/lib/contexts/operations-context.tsx:1054` (shared
  `updateTimeoutRef`), non-critical branch ~`:1125`. The critical/location path
  already does the right thing via `pendingUpdatesRef`.
- **Fix direction:** per-incident timers, or route all updates through the same
  merge-into-`pendingUpdatesRef` mechanism the critical path uses.

### C2 — Network-failed mutations report success
- **What:** On the final network-error retry, the API client does
  `return undefined as T` instead of throwing (to dodge the Next.js overlay). For
  mutations this means the caller's `catch` (rollback/toast/refresh) never runs:
  status changes keep their optimistic state, crew/vehicle/material removals vanish
  locally but stay assigned server-side, reorders silently don't persist. UI lies
  until the next successful sync. Compounds C1.
- **Where:** `frontend/lib/api-client.ts:205-213`.
- **Fix direction:** throw a typed `NetworkError` for mutations; keep the
  soft-`undefined` behaviour only for polling GETs.

### C3 — Geofence notification type violates the DB CHECK constraint
- **What:** `_check_geofence_alerts` inserts `Notification(type="vehicle_arrived")`,
  but that value isn't in the `valid_notification_type` constraint (nor the response
  enum). When a tracked vehicle arrives on scene, `GET /api/notifications` hits an
  IntegrityError and **all** pending alerts (overdue, no-personnel, fatigue) roll
  back with it — the alert panel goes dark. Currently *dormant* because the check
  bails unless Traccar/GPS is configured, but it's a landmine the day GPS is enabled.
- **Where:** `backend/app/services/notification_service.py:475`; constraint at
  `backend/app/models.py:614`; enum at `backend/app/api/notifications.py:28`.
- **Fix direction:** one migration to add `vehicle_arrived` to the constraint +
  the `NotificationType` enum (or map it to an allowed type).

### C4 — `/api/sync/*` gated on any authenticated user; leaks DB credentials
- **What:** Every sync endpoint uses `CurrentUser`, not `CurrentAdmin`. A
  viewer-role account (or shared demo login) can `POST /api/sync/apply/{table}` to
  write arbitrary rows into incidents/events/personnel/settings, point
  `railway_database_url` at a foreign DB, and `GET /api/sync/config` **returns the
  production `DATABASE_URL` including password**. Live even if we never use the sync
  feature — the endpoints are mounted.
- **Where:** `backend/app/api/sync.py:25,65,99,135,219,255,307,353,404`.
- **Fix direction:** change the dependency to `CurrentAdmin` on all write/config
  endpoints; redact credentials from the config response.

## DO — real, worth fixing (not urgent)

### H6 — Delete the legacy MVP router
- **What:** `app/api/routes.py` (backed by legacy `app/crud.py`) is still mounted
  after the modern routers. It owns the non-slash paths: `GET /api/incidents`
  returns **all incidents across all events — training, live, and soft-deleted,
  mixed**; `PUT /api/incidents/{id}` updates status with no StatusTransition, audit,
  auto-release, optimistic lock, or WebSocket broadcast. Confirmed the frontend
  never calls the non-slash path, so it's dead weight that only fires on a wrong/
  external call.
- **Where:** `backend/app/api/routes.py`, `backend/app/crud.py`, mounted at
  `backend/app/main.py:395`.
- **Action:** delete both files and the include; run the suite.

### Point 7 (H1) — Reko write endpoints unauthenticated
- **What:** `POST /reko/generate-link` has no auth dependency ("editor-only in
  practice" per docstring, but unenforced) — anyone reaching the backend can mint
  valid reko tokens for any incident. `PATCH /reko/{report_id}` (edit/submit a
  report) validates neither login nor token; `GET /reko/{report_id}` and
  `/reko/incident/{id}/reports` are open too. A leaked link → infinite fresh tokens
  + ability to rewrite recon reports that feed operator decisions and the slip.
- **Where:** `backend/app/api/reko.py:302` (generate-link), `:134` (PATCH), `:173`,
  `:201` (open GETs).
- **Fix direction:** `CurrentEditor` on generate-link; token-or-auth validation on
  the PATCH and the report GETs (mirror `intake.py` / `viewer.py`).

### H3 — Non-atomic status transactions
- **What:** `update_event_activity()` and `unassign_resource()` (called inside
  `auto_release`) each `commit()` mid-operation, inside larger operations that commit
  again at the end. A crash/disconnect mid-completion can leave status=abschluss with
  crew still assigned, no StatusTransition row, no audit entry. Narrow window (needs a
  crash mid-flow) but a real correctness hole.
- **Where:** `backend/app/crud/events.py:226`, `backend/app/crud/assignments.py:150`,
  `backend/app/crud/incidents.py:333`.
- **Fix direction:** use `flush()` not `commit()` in the helpers; let the outermost
  operation own the single commit.

### H4 — Sync image/Excel work blocks the async event loop
- **What:** `photo_storage.save_photo` (PIL decode/resize/encode) and all openpyxl
  export/import run synchronously in async handlers. A field crew uploading a 10 MB
  photo, or an editor pulling a large Excel export, freezes every request +
  WebSocket ping for all operators for the duration. (PDF report was already offloaded
  correctly — follow that pattern.)
- **Where:** `backend/app/services/photo_storage.py:186-202`,
  `backend/app/services/audit_export_service.py`,
  `backend/app/services/excel_import_export.py`.
- **Fix direction:** wrap the blocking work in `asyncio.to_thread(...)`.

### Points 11 & 12 — Wall display doesn't survive a long unattended session
Context: the display is set up when the emergency starts and then runs unattended for
hours — so both of these bite during exactly the window that matters.
- **11 — Bricks on a single failed refresh.** One failed data poll (Railway redeploy,
  brief blip) sets `error`, which renders a full-screen "Ungültiger oder abgelaufener
  Link" and **stops the refresh interval forever** — no recovery without a manual
  reload. Fix: distinguish initial-load failure from refresh failure; on refresh
  failure keep showing last-known data + a stale banner and keep retrying.
  Where: `frontend/app/viewer/page.tsx:293-303,353-358`.
- **12 — Listener leak on reconnect.** WebSocket listeners are re-attached (not
  replaced) on every reconnect; after N reconnects each update triggers N redundant
  full reloads, degrading the display over a multi-hour session. Fix: `socket.off(event)`
  before re-attach, or only register in `on()` and let socket.io buffer across
  reconnects. Where: `frontend/lib/websocket-client.ts:182-187`.

### Point 13 — Print jobs that fail or get stuck are lost forever
- **What:** The agent only fetches `status == "pending"`. A job that fails (paper out,
  cable pulled) is marked `failed` and never re-queued, with no retry button. A job
  claimed (`printing`) by the Pi that then loses power stays `printing` forever —
  invisible to both the pending query and the agent. The specific slip silently
  vanishes. (Slips aren't ultra load-bearing, but it's a known, safe, quick-ish fix,
  so worth doing.)
- **Where:** `backend/app/api/print.py:495-585`; `backend/app/crud/print_jobs.py`.
- **Fix direction:** a stale-`printing` reaper (requeue after a timeout) + a
  failed-job retry path (UI button and/or auto-requeue with a cap).

### Point 14 — Remove `create_all` from the boot path
- **What:** The lifespan (and seed) run `Base.metadata.create_all` on every boot
  alongside Alembic. A model added without a migration gets its table via `create_all`;
  the later real migration then fails with DuplicateTable → boot crash loop, and
  dev/prod schema drift goes unnoticed. Schema truth should be Alembic only.
- **Where:** `backend/app/main.py:141-144`, `backend/app/seed.py:59-64`.
- **Fix direction:** delete the `create_all` calls; rely on `alembic upgrade head`.

### Point 15 — Prod seed guards (weak default creds + fake live incidents)
- **What:** On a fresh/restored DB, boot-seed creates 7 **non-training** sample
  incidents (appear as real operations) and defaults `EDITOR_PASSWORD`/`VIEWER_PASSWORD`
  to `editor`/`viewer` with no production guard (unlike `ADMIN_SEED_PASSWORD`, which is
  enforced). Realistic trigger: restore into an empty DB, forget one env var → internet-
  facing `editor/editor` + fake incidents on the board.
- **Where:** `backend/app/seed.py:111-125` (creds), `:380-505` (sample incidents).
- **Fix direction:** refuse weak `EDITOR_/VIEWER_PASSWORD` defaults when
  `RAILWAY_ENVIRONMENT` is set; skip sample-incident seeding in production.

### Entra-ID auto-provision as editor
- **What:** We use Entra ID. Microsoft login auto-creates any unknown tenant user as
  `role="editor"` — full write access to live operations, no approval/allowlist. Any
  member of the tenant who reaches the login gets operator rights.
- **Where:** `backend/app/api/auth.py:378-390`.
- **Decision (final):** default new SSO users to `role="viewer"`; grant `editor` only
  to accounts on an explicit **editor allowlist**.
- **Fix direction:** change the auto-provision role from `editor` to `viewer`; add an
  editor allowlist (env var `SSO_EDITOR_ALLOWLIST` — comma-separated emails, matched
  case-insensitively — or a `settings` key so it's editable without redeploy). On
  login, if the user is new: create as `editor` if their email is on the allowlist,
  else `viewer`. Existing users keep their current role (don't downgrade on re-login).
  Decide whether an already-provisioned user whose email is *added* to the allowlist
  later gets auto-promoted on next login, or requires a manual role change (leaning:
  manual, to keep promotion an explicit act).

## DISCUSS — open decisions

### Point 16 — Degraded-internet / offline story
We're Railway-only; if the station uplink dies, board/map/intake/printing all die,
even with a healthy LAN. This is a **product decision, not a bug**. Two threads:

**(a) Always-on local instance (future).** Once a laptop runs at the command post, install
a small always-running Docker instance so non-technical users don't set anything up.
Open questions to resolve before building:
- Is it a read-only mirror (safe, simple) or a read-write local primary that syncs back
  to Railway (the dormant sync machinery — but see M3 below: it currently doesn't sync
  assignments/transitions/reko, so a naive failover shows incidents with no crews)?
- How do clients discover the local instance vs Railway (DNS/mDNS, a toggle, auto-detect)?
- Offline map tiles currently hardcode `http://localhost:8080` — only works on the tile-
  server host, and breaks under HTTPS. Would need a configurable tile URL.

**(b) Quick, semi-automated switch to paper (now).** We need an easy way to fall back to
a paper board without losing the picture — shape still TBD. Candidate building blocks
(low-tech, robust): a one-click "print/export current board snapshot" (incidents, roster,
vehicles, materials, contacts, key links) that an operator can run at outage onset, plus a
periodic auto-snapshot during larger events. This overlaps with the already-listed items
in [`docs/TODO.md`](TODO.md) (outage SOP, snapshot routine, paper board ready, failover
drill). **Next step: sketch the snapshot/export UX and the "we're on paper now" SOP.**

## KEEP IN MIND — deferred, revisit when relevant

- **M3 — Sync service correctness.** If/when we operationalise local sync (16a): batched
  pagination has no `ORDER BY` (can skip/duplicate rows); `incident_assignments`,
  `status_transitions`, `reko_reports`, users aren't in `SYNCABLE_MODELS`; the
  delta-window can miss records updated mid-sync; manual + scheduled sync share an
  in-memory flag and can run concurrently; settings sync bidirectionally (local toggles
  fight Railway's). Must be fixed *before* relying on failover, not after.
  `backend/app/services/sync_service.py`.
- **H5 — Duplicate active assignments race.** Two operators assigning the same vehicle
  within the same second both succeed (FOR UPDATE locks nothing when no row exists; unique
  constraint treats NULL `unassigned_at` as distinct). Low real-world frequency; UI already
  treats double-booking as an explicit decision. Add a partial unique index someday.
- **M1 — Optimistic locking unused.** `expected_updated_at` support exists but the frontend
  never sends it, so concurrent edits of the same incident silently last-write-win. Rare in
  a command post; wire it up if it ever bites.
- **Login rate limit** (3/min per shared NAT IP) — could lock out the 4th tablet at
  operation start. Confirm it actually triggers before treating as real.

## Testing (point 17)

E2E is too slow to gate CI right now — **keep it local**, just ensure the suite runs
green locally before releases. The higher-leverage gap is that **Vitest never runs in CI
at all** and the four highest-risk frontend modules (`operations-context`, `page.tsx`,
`api-client`, `websocket-client`) have zero tests. Minimum worth doing alongside the ASAP
batch:
- Add a Vitest step to CI.
- An `operations-context` unit suite covering the C1/C2 failure modes (assign-then-fail
  rollback, poll-during-cooldown doesn't clobber optimistic state, network-failed mutation
  surfaces an error) so those two can't silently regress.
- Backend already has strong pytest coverage; add a training-vs-live leakage regression and
  an `alembic upgrade head` vs `Base.metadata` drift test when convenient.

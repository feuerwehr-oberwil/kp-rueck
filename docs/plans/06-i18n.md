# Plan 06 – Internationalization (German + French)

**Priority:** P2 (post-publication; "FR geplant" can be announced in the article)
**Scope:** Frontend only (backend stays German – see "Backend strings" below).
**Estimated size:** Large (~69 files contain German strings, ~214+ literal
occurrences). Implement in the three phases below – **each phase is a separate PR**.

## Current state (verified)

- No i18n library in `frontend/package.json`.
- All UI strings are hardcoded German across ~69 files.
- Partial centralization exists: kanban column titles in
  `frontend/lib/types/incidents.ts:182` (`KANBAN_COLUMNS`: 'EINGEGANGEN', 'REKO',
  'REKO ABGESCHLOSSEN', 'DISPONIERT', 'EINSATZ', 'RÜCKKEHR', 'BEENDET').
- `date-fns` German locale used in `frontend/app/divera-pool/page.tsx`
  (`import { de } from 'date-fns/locale'`); `localeCompare('de')` in
  display/status, reko-dashboard, personnel-settings.
- 118 is read across Switzerland; Romandie departments need French. Italian is a
  later follow-up – the architecture must allow adding `it.json` by file-drop.

## Design decisions (final – do not change)

- **Library: `next-intl`** – the de-facto standard for Next.js 15 App Router,
  works in client and server components.
- **No locale URL routing.** Locale is stored in a cookie (`NEXT_LOCALE`) and a
  localStorage mirror, default `de`. This avoids touching the routing of an app
  that is heavily client-component based, and operational URLs stay stable
  (bookmarked display screens, QR-code check-in links).
- **Domain status values are NOT translated in data** – `eingegangen`, `reko` etc.
  are DB values. Only their **display labels** are translated.
- **Message files:** `frontend/messages/de.json` and `frontend/messages/fr.json`,
  organized by feature namespace (`common`, `nav`, `kanban`, `incidents`, `map`,
  `settings`, `login`, `events`, `reko`, `print`, `divera`, `notifications`,
  `help`, `errors`). German is the source of truth; a key missing in `fr.json`
  falls back to German (configure next-intl's `getMessageFallback`/fallback
  locale accordingly – fallback, not crash, and no console spam in production).
- **Swiss conventions in both languages:** German uses "ss" (no "ß"); French uses
  Swiss-French terms where they differ (e.g. "sapeurs-pompiers" usage is fine –
  have a francophone firefighter review `fr.json` before release; mark this as a
  manual step).
- Help-page markdown (`frontend/public/content/help/index.md`) is translated by
  **file convention**: `index.md` (de) and `index.fr.md`; the help page picks by
  locale with fallback to `index.md`.

## Phase 1 – Infrastructure + extract strings (behavior unchanged, still German-only)

1. `pnpm add next-intl`.
2. Setup without routing (follow next-intl's "App Router without i18n routing"
   guide): `frontend/i18n/request.ts` reads the locale from the `NEXT_LOCALE`
   cookie (default `"de"`), loads `messages/<locale>.json`; wrap the app in
   `NextIntlClientProvider` in `frontend/app/layout.tsx` (providers block,
   lines ~56-79).
3. Create `frontend/messages/de.json`. Extract strings **feature by feature**, one
   commit per area, in this order (highest-visibility first):
   1. `app/login/page.tsx`, `components/demo-banner.tsx`
   2. `components/page-navigation.tsx`, UserMenu, notification components
   3. Kanban: `app/page.tsx`, column/card components, `KANBAN_COLUMNS` labels
      (keep the const but source its `title` strings from messages – the const is
      imported widely; convert it to a function `getKanbanColumns(t)` or map
      status→`t(`kanban.columns.${status}`)` at render sites – choose the
      `t()`-at-render-site approach to keep the const's non-label fields intact)
   4. Dialogs: delete-confirm, incident detail, quick-incident
   5. `app/settings/**` (largest chunk)
   6. `app/events`, `app/map`, `app/reko*`, `app/divera-pool`, `app/display/*`,
      `app/help`, error pages (`app/error.tsx`, `RouteError`)
6. Replace literals with `useTranslations("<namespace>")` →
   `t("key")` in client components; `getTranslations` in any server components.
   **Toast strings inside `lib/contexts/*.tsx` and `lib/api-client.ts`** are
   called outside React – for these, create `frontend/lib/i18n-messages.ts`
   exposing a `translateOutsideReact(key)` helper backed by the loaded messages
   (next-intl's `createTranslator` with the active locale); keep it thin.
7. Centralize date-locale: `frontend/lib/date-locale.ts` exporting
   `getDateFnsLocale()` (de ↔ fr from `date-fns/locale`); replace the direct
   `de` imports; replace `localeCompare('de')` with `localeCompare(activeLocale)`.

**Phase 1 definition of done:** zero user-visible change; `grep` for a sample of 20
previously hardcoded strings finds them only in `de.json`.

## Phase 2 – French translation

1. Create `fr.json` mirroring `de.json` key-for-key. Machine-translate as a first
   pass is acceptable, but flag for native review (PR checklist item).
2. Add `frontend/public/content/help/index.fr.md`.
3. Add the key-parity check script (see Tests) to CI (`package.json` script
   `i18n:check`, run it inside `pnpm test` via a Vitest test – simplest).

## Phase 3 – Language switcher

1. Settings → General section (`frontend/app/settings/page.tsx`, `SECTIONS`
   mechanism at lines 92-103 – extend the existing General panel, no new section):
   a select "Sprache / Langue" with Deutsch / Français. On change: set the
   `NEXT_LOCALE` cookie (1-year expiry), then `router.refresh()` (and a full
   `window.location.reload()` if client-cached strings persist – test which is
   needed; prefer the lighter option that fully switches).
2. Login page: small DE | FR text toggle in the footer (readers from Romandie must
   be able to switch **before** logging in).

## Test plan

- **Key parity (Vitest, `frontend/lib/i18n.test.ts`):** recursively collect key
  paths of `de.json` and `fr.json`; assert sets are equal (after Phase 2). Until
  then, assert `fr` ⊆ `de`. Also assert no empty-string values and that
  ICU-placeholder sets match per key (`{count}` etc. – regex `\{(\w+)\}`).
- **Unit tests keep passing:** existing RTL tests assert German strings (e.g.
  delete dialog "Löschen"). Add a shared test wrapper
  (`frontend/test-utils/render-with-intl.tsx`) that wraps render in
  `NextIntlClientProvider` with `de.json`, and migrate failing tests to it.
  Assertions may keep literal German – `de.json` is the source of truth and tests
  pin it intentionally.
- **Smoke unit test:** render the login page with `fr` messages → French title
  visible, no missing-key error.
- **E2E (new `frontend/tests/e2e/19-i18n/language-switch.spec.ts`):**
  1. Visit `/login` → German by default.
  2. Click FR toggle → form labels switch to French (assert one known string).
  3. Reload → French persists (cookie).
  4. Log in, open Settings → switch back to Deutsch → nav labels German again.
- **Regression:** full existing E2E suite must pass with default locale `de`
  (proves Phase 1 changed nothing observable).

## Backend strings (explicit non-goal, with one guard)

Backend error `detail` strings remain German and are sometimes shown in toasts.
Do **not** translate the backend. Where the frontend displays backend `detail`
verbatim for known error cases (409 conflict, 401), it already substitutes its own
copy – keep that pattern: frontend-owned messages for known status codes, raw
detail only as last-resort fallback.

## Acceptance criteria

- [ ] Phase 1 merged with zero visual diff (spot-check 5 screens against `main`).
- [ ] Phase 2: `i18n:check` parity test green; native-review checklist noted in PR.
- [ ] Phase 3: switching is persistent across reload and login; no mixed-language screens (spot-check kanban, settings, map in FR).
- [ ] All suites green: `pnpm test`, `pnpm lint`, `pnpm exec tsc --noEmit`, E2E.

## Out of scope

- Italian (`it.json`) – architecture supports it; not in this plan.
- Translating seeded demo data (incident titles stay German – they're data).
- Backend/API i18n, printed thermal tickets (printer output stays German).
- PDF report translation (plan 07 reads its strings from a small dict – keep German there until this plan lands, then wire it to the locale as a follow-up).

Ausgangslage

Der Member-Sync holt die Divera-ID jeder Person bereits ab (data.cluster.consumer-Key = user_cluster_relation-ID in divera_members.py:73) — wirft sie aber weg. Die bestehende Divera-Integration ist rein eingehend (Poller/Webhook → divera_emergencies → manuell an Event hängen). Der vorhandene divera_access_key liest bereits Mitglieder via pull/all → ist also sehr wahrscheinlich ein Vollzugriff-Key. Der Grossteil der Arbeit ist: vorhandene ID speichern + defensiver Outbound-Client.

⚠️ Pager dürfen nicht doppelt auslösen

fwo-divera betreibt eine e-Call-Brücke (Divera-Webhook → Resend → Pager-SMS), die bei jedem Divera-Alarm pagt und nur foreign_id mit Präfix fwo-sms überspringt. Ein neuer KP-Rück-Alarm würde sonst die Pager erneut auslösen.

🔴 Lektion: notification_type ist das Sicherheitsfeld

1=ausgewählte Standorte (PRO) · 2=ALLE des Standortes ⚠️ NIE verwenden · 3=ausgewählte Gruppen · 4=ausgewählte Benutzer. Für Einzelausalarmierung immer notification_type:4. user_cluster_relation gilt nur bei 1 oder 4. Ohne notification_type lehnt Divera sicher ab („Sie müssen einen Empfänger auswählen") — sicherer Fehlerfall. Der Code muss 2 hart ausschliessen.
